# Data Model: Pre-order Bulk Actions

**Classification**: CONFIDENTIAL (describes real payment, shipment and audit structures)

## Schema changes

**None.** No migration, no new table, no new column.

| Need | Where it lives |
|---|---|
| Bulk Operation identity | `bulk_ref` (UUID generated by the server per apply) inside `activity_logs.new_values` of the per-pre-order rows and of one aggregate row |
| Payment idempotency key | existing `payments.client_ref` (UNIQUE across modes), derived per pre-order (UUIDv5 of the dialog's `batch_ref` + pre-order id) |
| Per-pre-order change record | existing `activity_logs` (`user_id`, `action`, `entity_type='Preorder'`, `entity_id`, `old_values`, `new_values`, `created_at`) |
| Result of a run | response only (not stored); the audit rows are the durable record |

Why no `bulk_operations` table: the spec's "Bulk Operation" needs identity, who/when/what and counts — all carried by the
aggregate log row plus `bulk_ref` on the per-pre-order rows. A table would need `HasDataMode` and a `CloneRegistry` entry (see
064 research D4) for no extra capability; revisit only if a "list all bulk operations" screen is ever required.

## Entities

### Pre-order (existing, `preorders`)
Changed only through the existing writers: `status` / `cancel_reason` (`transitionStatus`), `dispatch_status` /
`invoice_sent_at` / `shipping_at` (extracted `setDispatchStatus`), payment cache columns (`PaymentService`). No new field.

Status lifecycle (unchanged, `Preorder::ALLOWED_TRANSITIONS`):

```
ordered → dp_paid | cancelled
dp_paid → arrived | cancelled
arrived → settled | cancelled
settled → handed_over
handed_over, cancelled → (terminal)
```
Marker (unchanged): `pending | invoice_sent | shipping`; `shipping` only when `fulfillment = courier`; not for `cancelled`.

### Payment (existing, `payments`)
One row per payment via `PaymentRecorder`; bulk produces ordinary rows: `preorder_id`, `method`, `channel_id`, `purpose`,
`amount`, `verification` (`verified` for cash, else `pending`), `paid_at = now()`, `reference`, `notes`, `client_ref`
(derived), `recorded_by`. No proof, no editable date in bulk (spec amended).

### Shipment (existing, `shipments`)
At most one per pre-order (existing rule): `preorder_id`, `courier_name`, `tracking_number`, `shipping_cost`,
`recipient_name`, `recipient_phone`, `address_line`, `province`, `notes`, `status` (default; not changed by this feature).

### Audit Entry (existing, `activity_logs`)
New `action` values written only by the bulk path (all with `new_values.bulk_ref`):

| action | entity | written | `old_values` / `new_values` |
|---|---|---|---|
| `preorder_bulk_status` | `Preorder` id | inside the pre-order's transaction | `{status}` → `{status, cancel_reason?, bulk_ref}` |
| `preorder_bulk_dispatch` | `Preorder` id | same | `{dispatch_status, invoice_sent_at, shipping_at}` → new values + `bulk_ref` |
| `preorder_bulk_shipment` | `Preorder` id | same | — → `{shipment_id, courier_name, tracking_number, bulk_ref}` |
| `preorder_bulk_payment` | `Preorder` id | same | — → `{payment_id, amount, method, status, remaining, bulk_ref}` (the service's own `payment_recorded` row also exists) |
| `preorder_bulk_operation` | none (`entity_id` null) | after the loop | `{bulk_ref, action, params, selected, succeeded, skipped, failed, skipped_by_reason}` |

### Bulk Operation / Bulk Item Result (virtual)
Not stored. Response shape in the contract; `bulk_ref` ties the audit rows together.

## Derived values (no new storage)

- Outstanding / payment status: `PaymentSummary` (the single source; used by the payment preview).
- Status choices with counts: from `PreorderService::statusBlocker()`.
- Shipment recipient defaults: `ShipmentService::recipientDefaults()`.

## State transitions

Bulk adds none. Each action performs the existing transition for each pre-order or skips it.

## Validation rules (server)

- `order_ids`: array of distinct integers, 1…`preorders.bulk_max`.
- status: `status` ∈ `dp_paid, arrived, settled, handed_over, cancelled`; `cancel_reason` required when `cancelled` (≤ 255).
- dispatch: `dispatch_status` ∈ `pending, invoice_sent, shipping`.
- payment: `batch_ref` UUID; shared `method` ∈ `cash, bank_transfer, qr_ewallet`, `channel_id` required for non-cash (and must exist),
  `reference` ≤ 100, `notes` ≤ 1000; `rows[]` = `{preorder_id, amount > 0}` with distinct ids ⊆ `order_ids`.
- shipment: shared `courier_name` (required, ≤ 50), optional `shipping_cost ≥ 0`, `notes`; `rows[]` = `{preorder_id, recipient_name ≤ 100,
  recipient_phone ≤ 30, address_line ≤ 255, tracking_number? ≤ 50}`.
  Shape errors are `422` before anything is processed; rule violations per pre-order are skips.

## Clone LIVE → DEMO and backups

Nothing new is stored, so `CloneRegistry` and backups are unaffected. (`activity_logs` is administrative data, not cloned.)
