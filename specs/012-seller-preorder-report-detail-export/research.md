# Phase 0 Research: Seller Recap Preorder Detail, Richer Pre-order Report & Missing Report Exports

## R1 — Merging preorder transactions into the seller transaction-detail view

**Decision**: `artistSettlementTransactions()` gets a second, parallel query over `preorder_items` joined to `preorders` and `payments` (same `leftJoinSub`-summed-collected-amount pattern `010`'s `preorders()` already established), filtered to `preorder_items.artist_id = $artist->id`, `preorders.event_id = $eventId`, `preorders.status != 'cancelled'`, and an explicit `preorders.data_mode = ModeGate::current()` / `preorder_items.data_mode = ModeGate::current()`. Each preorder is shaped into the *same* transaction-entry structure the Order query already produces (`{key, number, created_at, items: [{sku, name, qty, line_total}], amount_for_artist, source}`), with a new `source: 'order'|'preorder'` discriminator field and the entry's identifying key renamed generically (`key` instead of `order_id`, since a preorder entry has no `order_id`) so `ArtistTransactionsModal.vue`'s `:key` binding and rendering don't collide across the two sources. The two collections are concatenated and re-sorted by `created_at` descending before being returned, exactly mirroring how `010`'s `sales()`/`profit()` already merge two aggregate sources in PHP rather than a SQL `UNION`.

**Rationale**: Confirmed via code read that `artistSettlementTransactions()` (ReportController.php:518-574) is a single `OrderItem`-only query with no preorder awareness at all, and that `ArtistTransactionsModal.vue` renders each entry keyed by `tx.order_id` — a field that literally doesn't exist for a preorder-sourced entry, so the shape must be normalized before it reaches the component rather than patched at render time. Using the `010`-established collected-amount computation (not `preorder_items.line_total` unprorated) keeps this feature consistent with FR-002/FR-003's requirement that the detail sum must equal the seller's already-correct (010-fixed) Seller Recap total — using a different, unprorated figure here would make the two numbers disagree, reintroducing the exact "total doesn't match its own detail" problem this feature exists to fix.

**Alternatives considered**: *A single `UNION ALL` SQL query* — rejected; `OrderItem` and `PreorderItem` have different column sets (e.g. `discount_amount` exists only on `OrderItem`, confirmed in `010`'s research R1's own resolution of the identical problem for `sales()`/`profit()`), which forces awkward NULL-padding; `010` already chose "merge two queries once in PHP" for the exact same asymmetry and this feature stays consistent with that precedent rather than introducing a second merge strategy.

**Also fixed in the same touch**: `artistSettlementTransactions()`'s existing `OrderItem`/`orders` query has **no explicit `data_mode` filter at all** — a real, pre-existing gap independent of this feature's own scope, caught by the pre-plan code survey. Per this codebase's own established rule ("hand-rolled joined queries don't inherit Eloquent's global scope"), this is added as part of the same method edit rather than left to compound with the new preorder query's own explicit filter.

## R2 — Per-seller breakdown for the Pre-order report requires joining `preorder_items`, not an extra `GROUP BY` column

**Decision**: `preorders()` gains a new query path (triggered by an optional request param, e.g. `?breakdown=artist`, or as an always-included second result set — see R4 for the export shape decision) that joins `preorder_items` (on `artist_id`) to the existing `preorders`+`payments`-collected-subquery structure, and re-derives `total_order_value`/`total_collected`/`total_outstanding` **per artist** by prorating each preorder's header-level amounts across its items' value share for that artist — the exact same proportional-allocation rule `010`'s research.md R1 established for `sales()`/`profit()`/`SettlementService`, applied here at report-generation time instead of report-storage time.

**Rationale**: Confirmed via code read that the current `preorders()` query (ReportController.php:796-840) aggregates at the `preorders` header level with zero join to `preorder_items` — there is no artist dimension anywhere in the current query, so this genuinely is a new join and a new per-row computation, not a cosmetic addition. Reusing `010`'s already-battle-tested (and already-tested-with-a-concrete-numeric-example) proration rule avoids inventing a second attribution method for the same underlying question ("how much of this preorder belongs to this artist") that `010` already answered for report totals.

**Alternatives considered**: *Attribute a preorder's full value to whichever artist has the largest item share ("winner takes all")* — rejected; produces a per-seller breakdown that doesn't sum back to the same preorder's true collected amount when a preorder spans multiple artists, undermining FR-002 of `010`'s own spec (never inflate revenue) applied here in reverse (never misattribute revenue to the wrong seller either).

## R3 — Pre-order report drilldown mirrors the Stock-by-Seller detail pattern exactly

**Decision**: A new `PreorderReportDetailModal.vue` component follows `StockByArtistDetailModal.vue`'s exact structural pattern: props `open`, plus the summary row's grouping keys (`status`, `paymentCompleteness`, optionally `artistId` once R2 ships); a `watch` on `[open, ...keys]` that calls the same `preorders()` endpoint with those keys as filter params (returning individual-preorder rows instead of the aggregate), on-demand only — never eagerly fetched for every row up front.

**Rationale**: `StockByArtistDetailModal.vue` (added in `009`) is the most recent, directly-analogous precedent in this exact codebase for "click a summary report row → see the individual records behind it," reusing the same underlying report endpoint with an extra filter param rather than standing up a parallel detail endpoint — the same shape this feature's drilldown needs.

**Alternatives considered**: *A dedicated `GET /reports/preorders/{status}/{completeness}/detail` endpoint* — rejected; `009`'s precedent (and Constitution I's "no duplicated write/read path for the same concern") already established that a summary endpoint's detail mode is expressed as an optional filter param on the same endpoint, not a new route.

## R4 — Selecting an individual preorder from the drilldown reuses the existing deep-link mechanism

**Decision**: Clicking a preorder row inside `PreorderReportDetailModal.vue` navigates to `/preorders?preorder_id=<id>` (router push), reusing `PreordersView.vue`'s already-working `onMounted` handler that reads `route.query.preorder_id`, calls `openDetailById(id)`, and strips the query param afterward.

**Rationale**: Confirmed via code read (`PreordersView.vue:69-76`, `openDetailById` at line 325-338) that this exact mechanism already exists and was built for precisely this "arrive at a specific preorder's detail from somewhere else in the app" use case (originally for `009`'s `CustomerTransactionsModal.vue`). Reusing it directly satisfies FR-008's "reuse the existing detail view, not a new one" requirement with zero new navigation code.

**Alternatives considered**: *Render a lightweight preorder-summary directly inside the drilldown modal itself* — rejected; would duplicate fields (`PreordersView.vue`'s detail drawer) this codebase already renders correctly elsewhere, and the existing deep-link mechanism already solves this exact navigation need.

## R5 — Export shape for the three missing exports differs by report complexity

**Decision**: Purchases and Stock-by-Seller exports use `GenericArrayExport` directly (single flat sheet, headers inferred from row keys) since both `purchases()` and `stockByArtist()`'s summary-mode response are already flat, unnested arrays. The Pre-order export uses the `MultiSheetArrayExport`/`SheetArrayExport` pattern (mirroring `exportArtistSettlements()` exactly) with two sheets: "Ringkasan" (the existing status × payment-completeness rows) and "Per Seller" (the new R2 breakdown rows) — because FR-011 explicitly requires the export to include the per-seller breakdown alongside the existing summary, and `GenericArrayExport` has no multi-sheet capability.

**Rationale**: Confirmed via code read that `GenericArrayExport` (single `FromArray`/`WithHeadings`, headers inferred) is a correct, already-used fit for flat single-shape data (used today for `sales`, `profit`, `artist-profit`), while `exportArtistSettlements()` already solves the exact "one summary sheet + one detail sheet" shape this feature's Pre-order export needs, via `MultiSheetArrayExport`+`SheetArrayExport` (explicit headings, order-safe row-to-heading mapping — safer than `GenericArrayExport`'s key-inference for a sheet that could have zero rows in one status bucket). No new export infrastructure is needed either way.

**Alternatives considered**: *Two separate export buttons/downloads for the Pre-order tab (one for the summary, one for the per-seller breakdown)* — rejected; FR-011 asks for one export of "that report's rows," and a single two-sheet workbook is both simpler for the user (one download, one file) and consistent with the `exportArtistSettlements()` precedent for exactly this kind of "summary + breakdown" report.

## R6 — Backend export whitelist and frontend wiring need no new abstraction

**Decision**: `ReportController::export()`'s whitelist (currently `['sales', 'profit', 'artist-settlements', 'artist-profit']`) gains `'purchases'`, `'stock-by-artist'`, `'preorder'`. Three new `<BaseButton>` call sites are added in `ReportsView.vue`, copy-pasting the existing pattern (`v-if="activeTab === '<tab>'" @click="doExport('<report-type>')"`) with no change to `doExport()` or `exportReport()` (both already fully generic — confirmed via code read, `exportReport()` builds its request URL/filename from the `report` string parameter alone).

**Rationale**: The controller's `in_array(...)` whitelist gates which report types are exportable, extended the same way for both new backend flags. **Correction during implementation**: this research entry originally claimed the route (`routes/api.php:174`) had no `where()` constraint on `{report}` — that was wrong. The route DOES carry `->where('report', 'sales|profit|artist-settlements|artist-profit')`, and the new export types 404'd at the routing layer until that regex was also extended to include `|purchases|stock-by-artist`. Both the controller whitelist and the route regex needed updating, not just the former.

**Alternatives considered**: None needed — this is a direct, mechanical extension of an already-generic system, not a design choice.
