# Feature Specification: Edit Variant Sequence Number Manually

**Feature Branch**: `053-variant-sku-manual-edit`

**Created**: 2026-10-17

**Status**: Draft (clarified: product code fixed, sequence editable; typed numbers kept on a segment change, codes follow the product; updated 2026-10-17: variants listed in SKU order)

**Input**: User description: "in product edit, update so that i can update the variant sku manually" (with a screenshot of the product edit drawer: each variant card shows its SKU as a read-only chip such as `SPF-PI-S-1`, next to the variant's name, stock and prices)

## Current behaviour (for reference)

- The product edit drawer shows each variant's SKU as a read-only chip in the variant card header.
- Variant SKUs are generated by the server: the product code, a hyphen, and the next number (feature 044). The owner cannot type or change a SKU.
- A segment change regenerates every variant SKU (feature 044, User Story 3).

## Decisions

- **Product code is fixed.** The product code (for example `SPF-PI-S`) is shown in the variant card and cannot be edited there. Only the sequence number after it can be changed.
- **Typed sequence numbers survive a segment change.** A variant whose sequence number was typed by the owner keeps its number when the product's segment changes; its code follows the product's new code. Generated SKUs follow the segment change as before (feature 044).

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Type a variant's sequence number in the edit drawer (Priority: P1)

In the product edit drawer, the owner can change a variant's sequence number. The product code in front of it is shown as fixed text. Saving the drawer stores the new SKU.

**Why this priority**: The owner's stock sheets, labels and supplier codes use numbers the owner chose; the generated number does not always match them.

**Independent Test**: Edit a variant whose SKU is `SPF-PI-S-1`. The code `SPF-PI-S` is shown as fixed text and `1` is editable. Type `7`, save. The variant now shows `SPF-PI-S-7` in the list, the drawer, and the Stock screen.

**Acceptance Scenarios**:

1. **Given** a saved variant with SKU `SPF-PI-S-1`, **When** the owner changes the sequence number to `7` and saves, **Then** the variant shows `SPF-PI-S-7` everywhere it is listed.
2. **Given** the variant card, **When** the owner looks at the SKU, **Then** the product code is shown as fixed text and cannot be edited.
3. **Given** a new variant added in the drawer, **When** the owner types a sequence number, **Then** that SKU is used when the product is saved; an empty sequence uses the generated number.
4. **Given** the owner types a sequence number that gives a SKU already used by another variant, **When** they save, **Then** the save is refused with a message on that variant's sequence field and nothing changes.
5. **Given** the owner clears the sequence number of a saved variant, **When** they save, **Then** the save is refused with a message that a number is required (the variant keeps its current SKU).
6. **Given** a variant with past sales, **When** its sequence number is changed, **Then** those sales still show the SKU they were recorded with.

---

### User Story 2 - The sequence number is checked before saving (Priority: P1)

The sequence number is a whole number: digits only, at least 1, with no leading zeros kept (`007` is stored as `7`). The complete SKU, product code included, is at most 14 characters, and unique across the whole store (DEMO and LIVE, including deleted variants).

**Why this priority**: SKUs are read by scanners, imports and reports; a malformed or duplicate SKU breaks them silently.

**Independent Test**: Type `A7` in the sequence field, save: refused with a message about digits only. Type a number that makes the SKU longer than 14 characters: refused with a message about the length.

**Acceptance Scenarios**:

1. **Given** a sequence with a letter or symbol (for example `A7`), **When** saved, **Then** the save is refused with a message on the sequence field.
2. **Given** a sequence that makes the full SKU longer than 14 characters, **When** saved, **Then** the save is refused with a message on the sequence field.
3. **Given** the sequence `007`, **When** saved, **Then** it is stored as `7`.

---

### User Story 3 - Typed numbers survive a segment change (Priority: P2)

When the owner later changes the product's segment, every variant keeps its number and takes the product's new code. A typed number is not overwritten; the code is always the product's.

**Why this priority**: The owner chose these numbers on purpose; a segment change must not overwrite them. The code is never the owner's choice (FR-009), so it must follow the product.

**Independent Test**: Product `SPF-PI-S` with variant `SPF-PI-S-7` (typed) and variant `SPF-PI-S-2` (generated). Change the segment to `T`. Both variants keep their numbers: `SPF-PI-T-7` (typed) and `SPF-PI-T-2` (generated).

**Acceptance Scenarios**:

1. **Given** a variant whose number was typed, **When** the product's segment changes, **Then** its number stays and its code becomes the product's new code.
2. **Given** a variant whose number was generated, **When** the product's segment changes, **Then** its SKU is regenerated from the new code with the same number (feature 044).
3. **Given** a typed number that collides with a generated number under the new code, **When** the segment changes, **Then** the typed number is kept and the generated variant takes the next free number.

---

### User Story 4 - Variants listed in SKU order (Priority: P2)

In the product edit drawer, the variant cards are listed in SKU order, so the owner can scan a product's numbers in sequence: `…-1`, `…-2`, … `…-9`, `…-10`, `…-11`. Numbers compare as numbers, not as text, so `…-10` comes after `…-9`.

**Why this priority**: The owner reads and edits numbers in order, especially when shifting them (User Story 1 shifts). A random order makes a shift hard to check.

**Independent Test**: Open a product with numbers 1, 2, 9, 10, 11 (in any stored order). The cards appear as `…-1`, `…-2`, `…-9`, `…-10`, `…-11`.

**Acceptance Scenarios**:

1. **Given** a product whose variants are stored as `…-10`, `…-2`, `…-1`, **When** the owner opens its edit drawer, **Then** the cards appear as `…-1`, `…-2`, `…-10`.
2. **Given** the owner saves a shift that changes the numbers (`…-10` → `…-11`), **When** the drawer reloads, **Then** the cards are in the new SKU order.
3. **Given** a variant added or duplicated in the drawer that is not yet saved, **When** the owner has not saved yet, **Then** the new card stays where it was added; it moves into SKU order after the save.

---

### Edge Cases

- A new variant with an empty sequence field uses the generated number, as today.
- Typing the variant's current number is not a change and is accepted.
- A SKU that matches a deleted variant is refused, the same as an active one.
- A typed SKU's code follows the product's segment changes like every other SKU; only its number is kept. (Changed 2026-10-17; the earlier "keeps the old code" rule was rejected.)
- Excel import: a SKU in the sheet that does not match any existing variant is handled as today.
- A variant with no hyphen in its SKU (legacy format) has no number to compare; it sorts by its full SKU text, after the numbered variants of the same code.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: In the product edit drawer, each existing variant and each new variant MUST show its product code as fixed text and let the owner type only the sequence number after it.
- **FR-002**: The sequence number MUST be a whole number of digits only, at least 1; leading zeros are removed on save. The complete SKU (product code, hyphen, number) MUST be at most 14 characters.
- **FR-003**: A SKU MUST be unique across all variants, including deleted variants and both DEMO and LIVE data. A duplicate is refused with a message on the sequence field.
- **FR-004**: A saved variant MUST keep a SKU; clearing a saved variant's sequence number is refused.
- **FR-005**: Saving the drawer with a typed sequence number MUST store that SKU; a new variant with an empty sequence uses the generated number.
- **FR-006**: Changing a variant's SKU MUST NOT change any sales, stock or order history; recorded snapshots keep the SKU they were recorded with.
- **FR-007**: Every SKU change MUST be recorded in the activity log, with the old and new SKU.
- **FR-008**: Refusals MUST show the message on the sequence field of the variant concerned; nothing in the drawer is saved when any SKU is refused.
- **FR-009** (decided): every SKU starts with its product code at the time it was set. The product code cannot be edited in the variant field.
- **FR-010** (decided, revised 2026-10-17): when the product's segment changes, every active variant takes the new code and keeps its number, typed or generated. If two variants would get the same number, the typed one keeps it and the other takes the next free number. Removed and deactivated variants are not changed.
- **FR-012**: The product edit drawer MUST list the saved variants of the product in SKU order: first by the code text before the last hyphen, then by the number after it, compared as whole numbers (`…-2` before `…-10`).
- **FR-013**: After a save, the drawer MUST show the saved variants in SKU order, including any change of number made in that save.
- **FR-014**: Variants that are not yet saved (added or duplicated in the drawer) MUST stay where they were added until the product is saved.
- **FR-011**: The system MUST remember, for each variant, whether its SKU was typed by the owner or generated, so that FR-010 can be applied.

- **FR-015** (decided 2026-10-17): the trash button on a saved variant REMOVES it when it has no history (sales, pre-order items, stock movements, BOM lines). Removed variants disappear from the drawer and lists. A variant with history is only deactivated, and the screen says so.
- **FR-016** (decided 2026-10-17): the number of a removed variant may be used again, by a typed number or by the generated number. Past sales keep the SKU text they were recorded with. This supersedes the "never reused after deletion" rule of feature 044 for removed variants.

- **FR-017** (decided 2026-10-17): a deactivated variant (kept because it has history) is hidden from the edit form and does not hold its number. SKU uniqueness, typed numbers and generated numbers consider active variants only. Enforced by a database rule on active variants; reactivating a variant is refused when an active variant already uses its number.

### Key Entities *(include if feature involves data)*

- **Product variant**: has a SKU (product code, hyphen, number) and a marker saying whether the SKU was typed by the owner or generated; unique across the store.
- **Activity log entry**: records each SKU change with the old and new value.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Owners can change the sequence number of any variant from the product edit drawer in under 30 seconds, without leaving the drawer.
- **SC-002**: 100% of duplicate, non-numeric or over-long sequence entries are refused on save, with the message on the sequence field.
- **SC-003**: 100% of past sales and stock records keep their recorded SKU after any SKU change.
- **SC-004**: 100% of SKU changes appear in the activity log with the old and new value.
- **SC-005**: 100% of variants with a typed number keep that number through a later segment change.
- **SC-006**: In 100% of checks, the saved variants of a product appear in ascending number order in the edit drawer, including after a shift saved in one step.

## Assumptions

- Uniqueness compares the complete SKU string. Leading zeros are removed before the check, so `007` and `7` are the same number.
- The 14-character limit is the stored width of the SKU column (feature 044).
- Storing whether a SKU was typed needs one new flag per variant; all existing variants are marked as generated.
- Excel import of SKUs stays as it is today; importing a SKU that does not exist does not create a variant with that SKU in this feature.
- "Sort by SKU" means the natural order in FR-012 (numbers compare as numbers), not plain text order. ASSUMPTION: this is what the owner means; confirm if plain text order is wanted.
- The order applies to the variant cards in the product edit drawer. The product list page is unchanged by this feature.
- The drawer keeps its existing layout: the SKU chip becomes a fixed product code followed by an input for the number.
