01 Introduction What it is

A till built for a booth with more than one owner.

Most point-of-sale software assumes one shop, one owner, one cash drawer, and a reliable internet connection. An event merchandise booth breaks all four assumptions at once — so BoothPOS is built around them instead.

PILLAR 01

Every item knows its seller

A single basket can mix three artists' goods. Each sold line permanently records which seller it belonged to, at the price and cost it had that day — so the payout maths is already done before you close.

PILLAR 02

Everything hangs off the event

Sales, shifts, floats, profit and settlements are all scoped to a named event. "Was that convention worth going to?" is a report, not a guess.

PILLAR 03

The machine in front of you is the whole system

Database, server and screens all run on the shop's own laptop over localhost. There is no cloud tier to fail, and no outbound call in the selling path.

Commercially: BoothPOS is sold as a one-time licence installed locally, per store. There is no monthly fee, no multi-tenant service, and no vendor-side copy of your sales data.
01 Introduction The product at rest

The home screen answers the two questions a booth owner actually asks.

How are we doing right now, and who is owed what. Net sales, transaction count and gross profit for the running event sit above a live per-seller split, day-by-day takings, and breakdowns by category, seller and event.

  • Four shortcut tiles jump straight to a new sale, a new pre-order, a stock adjustment or a new product.
  • Results per seller updates as you trade — no report to run.
  • Low-stock and pending pre-order counters flag what needs attention before it becomes a problem.
DEMO — the amber badge in the header means this installation is in practice mode. Everything you see here is demo data that never touches the real books.

02 Problem Why a generic POS does not fit

The four assumptions ordinary till software makes.

ASSUMPTION 01

"One shop owns all the stock"

So there is nowhere to record that the keychain belongs to Hoshizora Craft and the standee belongs to Yukishiro Works — and no way to split one basket between them.

ASSUMPTION 02

"Trading is continuous"

So there is no notion of an event: no per-event float, no per-event profit after the booth fee, no way to compare one convention against another.

ASSUMPTION 03

"The internet is there"

So the moment the hall's wifi drops, the queue stops. Cloud tills degrade exactly when a booth is busiest.

ASSUMPTION 04

"You pay monthly, forever"

A subscription priced for a shop open 300 days a year is poor value for a booth that trades on six weekends.

The cost of getting this wrong is not abstract. The requirements document names artist payout disputes as a top project risk, and permanent data loss from an un-backed-up device as another. Both are settlement-and-evidence problems, which is why the audit trail and the per-seller drill-down are core features rather than extras.

03 Goals The promises

Seven commitments the build was measured against.

GOAL 01

Sell without the internet

The complete stack — database, application, screens — runs on the shop's machine. Reports, receipts and stock behave identically offline and online.

GOAL 02

Settle with each seller the same evening

Per-seller payout figures recalculated from live sale lines, with a transaction-level drill-down and an Excel export you can send to each artist.

GOAL 03

Never let the till decide what it earned

Prices, totals, discounts, cost of goods and stock deltas are computed server-side from master data. A client-supplied amount is never trusted.

GOAL 04

Make stock trustworthy enough to sell limited runs on

Per-variant stock, an append-only movement history recording the level before and after, and a row lock that prevents two simultaneous sales overselling the last unit.

GOAL 05

Answer "was this event worth it?"

Cost and sell price are frozen onto each sold line, so a price change today can never rewrite last month's profit. Event cost is subtracted to give a net figure.

GOAL 06

Be safe in the hands of a volunteer

Access granted screen by screen, three server-side authorization layers, and a practice mode so new staff can rehearse a whole event day without touching the real books.

GOAL 07

Cost one payment, not a subscription

A one-time licence, installed locally, in two tiers that run from the same single build: Pro for a single-seller booth and Master for unlimited sellers. Switching tiers is one setting — nothing already recorded is lost either way.

04 Methodology How it was built

Specification first, every single time.

PRACTICE 01

Nothing is built without a written spec

All 19 features live in their own numbered folder, each carrying a specification, an implementation plan, a research note and a task list — approved before any production code is written.

PRACTICE 02

Every non-obvious decision records its rejected alternatives

Research notes are written as numbered decisions in Decision / Rationale / Alternatives-considered form. When a report figure looks surprising, there is a documented reason rather than a shrug.

PRACTICE 03

A ratified engineering constitution

Five binding principles — code quality, testing, UX consistency, security, performance — with formal amendment rules. Where a feature genuinely had to bend one, the exception is written down and justified.

PRACTICE 04

Tests run against real MySQL, never a convenient fake

The suite runs against a real MySQL 8 database. This is enforced, not encouraged: several migrations use raw MySQL-only CHECK constraints that a lightweight substitute cannot even execute.

PRACTICE 05

Nothing is "done" until it is driven in a real browser

Screens must be exercised against the live API with the console checked before a task is closed. Three real reporting defects were caught this way that the automated suite had passed.

PRACTICE 06

A published bug log, each fix proven by a failing test

27 defects found during execution are logged with root cause and fix. Each was proven by a test that failed first and passed after — not by reading the code and declaring it fine.

04 Methodology Where the money is decided

The cashier's screen is never allowed to say what it earned.

This is the single most important design rule in the product, and the reason artist settlements can be defended in an argument.

What the till sends
Only which variant, and how many. Plus an optional discount and a one-time reference code.
What the server decides
The price of each line, from master data. The line total. Whether the discount is legal. The order total. The cost of goods, frozen onto the line. The change due. The stock delta. The receipt number.

Three consequences that matter commercially

  • Settlements cannot be manipulated from the counter. A cashier account cannot inflate what a seller is owed, because the cashier's screen never supplies a number that reaches the ledger.
  • Old reports do not drift. Cost and sell price are snapshotted onto each sold line, so re-pricing a product today leaves last month's profit exactly as it was.
  • A lost connection cannot double-charge. Each checkout carries a one-time reference; if the same one arrives twice, the original sale is returned untouched rather than rung up again.

The same rule governs stock: a single sanctioned write path locks the variant row, refuses a movement that would go below zero, and records the level before and after — including for the bulk spreadsheet import.

04 Methodology Practice mode

A whole second world on the same laptop.

One store-wide setting switches BoothPOS between DEMO and LIVE. Twenty transactional record types — orders, payments, stock movements, pre-orders, settlements and the rest — are stamped with the mode they were created in and filtered on every read.

  • Train a new cashier on a full, realistic shop — products, sellers, customers, sales, pre-orders — on the machine you will use for real money that weekend.
  • Rehearse an entire event day, including closing and reconciling the drawer.
  • Switch back to LIVE and every practice record disappears from every list, screen and financial report.
Why it is more than a demo toggle: reports that use hand-written database queries filter the mode explicitly, and values with a database-wide uniqueness rule — receipt numbers, pre-order numbers, product codes — are counted across both modes, so a practice sale can never collide with a real one.

Pictured: the activity log — who changed what and when, written inside the same database transaction as the change it records, so a rolled-back deletion can never leave a log entry claiming it happened.

05.1 Point of sale Opening the till

A shift with a counted float, tied to a named person and a named event.

No sale can be rung up outside an open shift, one person cannot have two shifts open at once, and a shift can only be opened against an event that is actually running.

  • Open Cashier Session, pick today's event and enter the cash in the drawer.
  • Optionally split that float by seller — the rows must sum exactly to the total, and the screen keeps them in lockstep so you cannot get it wrong.
  • Trade. Transaction count, total sales and cash taken are visible at any moment without closing anything.
  • At close, count the tin and type the figure. A difference demands a written note.
Worth knowing: the live payment-method breakdown reports verified cash only. Transfer and QRIS payments are recorded but stay marked pending, so they do not appear in that particular breakdown.
05.1 Point of sale Finding the item

A touch grid, narrowed by seller and category.

At a booth carrying three artists' ranges, the fastest path to the right item is to eliminate the other two. Filters are multi-select, and the search box matches product name or code as you type.

  • Tap a card, or type a name or product code into the search box.
  • Products with several sizes, colours or characters open a variant picker showing each variant's own item code, price and stock.
  • Pick the variant — it lands in the cart at the price the server holds for it, never a price the screen supplied.

05.1 Point of sale The multi-seller basket

One customer, one payment, three different artists paid correctly.

This is the feature the whole product exists for. The basket pictured holds a keychain from Hoshizora Craft, an enamel pin from Nekoyama Studio and an acrylic standee from Yukishiro Works. The buyer pays once. Each line lands in the right seller's ledger.

  • Add items from any sellers, in any order — nothing asks you to keep them separate.
  • Attach a customer, or leave it as a walk-in sale.
  • Enter an order-level discount if you are giving one; a discount larger than the subtotal is refused.
  • Park the basket with Save as draft if the buyer goes to find cash, and pick it up later.
Worth knowing: resuming a saved draft restores the items and discount, but not an attached customer — re-attach them before taking payment.
05.1 Point of sale Taking the money

Split one sale across cash, transfer and QRIS.

Half in cash and the rest by QR is an ordinary request at an event, and the till treats it as ordinary. Enter the first amount, commit it, and the panel shows the remaining balance and waits for the next method.

  • Pick a method. Cash offers tendered-amount shortcuts and computes change automatically.
  • Enter less than the total and the button becomes Add & continue — commit that part and choose another method for the rest.
  • For transfer or QRIS, the buyer sees the account holder and QR image; a photo of the proof is required before the sale can be saved.
  • Confirm. Payments totalling less than the amount due are refused by the server.
Pictured: Rp 50.000 already recorded in cash, Rp 72.000 remaining, QRIS selected and the confirm button held until proof is attached.
05.1 Point of sale The receipt

No thermal printer, no paper rolls, no power socket you do not have.

The receipt is drawn on screen in large, high-contrast type intended to be photographed by the buyer from their side of the table — and it can be re-opened from the sales list weeks later.

  • It carries your store identity, the event's name, location and dates, the transaction number and the cashier.
  • Split payments are itemised — the example shows Rp 20.000 by transfer and Rp 15.000 in cash.
  • Save it as an image or PDF if the buyer wants a copy.
  • Re-open any past receipt from Sales → View receipt.
Worth knowing: receipts are always printed in Indonesian, whatever language the interface is set to. The login and activation screens are too.
05.1 Point of sale Afterwards

Every sale, searchable, with the sellers named on the row.

Search filters instantly as you type across transaction number, customer, cashier and seller. Note the fourth row: a single transaction listing two sellers.

  • Click the transaction number, or View items, for the products sold.
  • Click View receipt to reopen the printable receipt.
  • Click a seller's name to filter the list down to their transactions.
  • Export .xlsx downloads a spreadsheet of the event's sales grouped by product.
Read the tiles carefully: the four headline figures include money already collected on pre-orders, while the list below is counter sales only — so the two will not reconcile at an event that took pre-orders.
05.2 Inventory Products

One product, many variants — each with its own code, price and stock.

A keychain design in Standard, Special Edition and Glow is one product with three variants. Price and stock live on the variant, because that is what actually sells out.

  • Give each seller and category a short code once, then add products — codes are generated for you.
  • The product list shows the shared 8-character product code; each variant's 12-character item code appears on its row in the edit panel and in the Detail pop-up.
  • Rename the product, seller or category later — the codes never move, so your price lists and old receipts stay valid.
  • Upload product photos; they appear on the till's cards.
05.2 Inventory Stock you can defend

An append-only history, not just a number.

Every movement records the level before and after, who did it, and what caused it. Six movement types cover the whole life of an item: initial, purchase, sale, pre-order handover, adjustment and return.

  • Filter the history by movement type to see only sales, only adjustments, or only pre-order handovers.
  • Correct a physical miscount with Stock adjustment — a reason is mandatory, and the entry is written to the audit log.
  • A movement that would push stock below zero is refused, naming the item and how many are actually available.
Worth knowing: a multi-line adjustment saves line by line rather than as one batch — if line three is rejected, lines one and two are already saved. Fix the rejected line and save it again. Low-stock thresholds are set through the Excel import, not on screen.
05.2 Inventory Moving in from a spreadsheet

One workbook, ten sheets, processed in dependency order.

"I already keep everything in a spreadsheet" is the most common reason a booth never switches systems. Sellers, categories, products, stock, suppliers, materials, prices, recipes, roles and users all arrive in one file.

  • Download the template — it ships with a worked example that imports as-is.
  • Paste your rows in and upload with preview ticked: a dry run walks the identical validation path and reports every problem by sheet, row, column and reason, changing nothing.
  • Fix what it names, then upload for real.
  • Export any time to get the same workbook shape back — exports round-trip through import.
All-or-nothing by design. A 500-row file with one typo imports nothing rather than leaving you half-migrated with no clear record of which half. The dry run is what makes that safe.
05.2 Inventory The supporting records

Sellers, categories, customers, events.

Deleting is guarded throughout: a record still referenced by real history cannot be removed, only deactivated. Removed records are soft-deleted, so history survives and the short code becomes free again.
05.3 Pre-orders The lifecycle

Take money now for goods that do not exist yet.

A pre-order runs through five guarded stages — Ordered → Deposit paid → Arrived → Settled → Handed over — with cancellation available along the way. Each step is checked against a strict state machine, so it cannot be skipped.

  • Record the customer, the items, the expected date and whether it is collection or courier.
  • Take a deposit; the order moves itself to Deposit paid on the first payment.
  • Mark Arrived when the goods land from the supplier.
  • Take the balance, hand over, and add courier and tracking details if it is shipping.
The rule people get backwards: creating a pre-order does not touch stock — the goods do not physically exist. Stock goes up on arrival and down on handover.
05.3 Pre-orders Money and paperwork

Deposits, instalments, and a document for every stage.

Handover is blocked until the balance is fully paid — and blocked again if someone sold the same item over the counter after it arrived, rather than driving your stock negative.
Email: marking a pre-order Arrived, Handed over or Cancelled emails the customer automatically. Deposit and settlement notices are sent on demand with Resend notification. Every attempt — sent, failed, or skipped because mail is not configured — is logged.
05.4 Reports The one that settles arguments

What you owe each artist, recalculated from live sale lines.

The stored settlement table is treated as a payment-status record and a cache — never as the source of truth for sales value. Open the report and every figure is re-derived from the actual order lines before anything is displayed.

  • Pick the event. Every seller shows units, sales, payable, paid, outstanding and a status.
  • Click a row for the individual transactions behind the total — counter sales and pre-orders together.
  • Record what you have handed over; the status re-derives itself to part-paid or paid.
  • Export .xlsx and send each artist their own copy, transaction detail included.
Every active seller is listed, even those who sold nothing — a zero row is a visible, checkable answer, where a missing row is an unanswered question.
05.4 Reports The other five tabs

Six report tabs, seven Excel exports.

THE RULE UNDER ALL OF THEM

Pre-order money counts only once it is really in the till

Revenue is taken from actual recorded payments, never the cached paid-amount field, then spread across the order's lines in proportion to each line's share of the value. A half-paid pre-order credits each seller exactly half. Cancelled ones contribute nothing.

05.5 Purchasing What an item really costs

A recipe per variant, priced from what your suppliers actually charge.

Record which suppliers sell each raw material and at what price, then attach the materials and quantities one unit of a specific variant needs. A large and a small keychain of the same design can need different amounts — so recipes hang off the variant, not the product.

  • Add suppliers and materials, then record a price per supplier-material pair.
  • Flag your usual supplier as preferred; flagging one automatically un-flags any other for that material.
  • Build the recipe on the variant. Quantities may be fractional — 0.25 of an acrylic sheet is a valid line.
  • Open the cost breakdown to see the material cost beside the cost price you typed in.
Deliberately read-only. The recipe cost never overwrites the cost price your profit reports and settlements already use. When several suppliers sell the same material, the preferred one's price is used — otherwise the cheapest.
05.5 Purchasing Restocking

Suppliers, materials and purchase orders.

Honest limits here. Material stock is tracked in the database but has no screen of its own yet. Supplier payments work in cash; the non-cash options on that form do not currently complete. Re-editing an existing draft's line items from the list is not reliable — cancel and re-create instead.
Where it does pay off today: knowing your true material cost per variant before you price it, keeping supplier price lists in one place, and having a printable order document to send.
05.6 Administration Who can see what

Roles are a list of screens, not a fixed four-way choice.

Four roles ship ready to use — Owner, Admin, Cashier and Inventory — but a role is just a set of menu permissions, so you can build your own.

  • The default Cashier gets the till, shift, events, customers, pre-orders and sales list — and pointedly not the profit or settlement reports.
  • Tick or untick individual screens to make a role that matches how your booth actually runs.
  • Staff accounts carry a photo and a last-access timestamp; each person manages their own password and photo from their profile.
Enforced on the server, in three layers — 45 request-level gates, 15 policy classes and inline role checks. A cashier cannot reach your margins even by calling the API directly, bypassing the screen entirely.
05.6 Administration Making it yours

Store identity, payment channels, and the safety net.

Payment channels

Your bank accounts and QRIS codes, with the QR image uploaded once and shown to the buyer at checkout. Account numbers are masked to the last four digits for anyone without settings access — a cashier can direct a payment without being able to read the full number.

Backup & restore

One command copies the database and the archive of payment-proof images to an external drive you nominate; a matching command brings them back. The backup is an ordinary MySQL dump — your data is never locked in a proprietary format.

05.7 Licensing How the product is protected

One licence, one installation — verified entirely offline.

A brand-new install is locked. Every screen bounces to activation, and the server independently refuses every request — including the login endpoint itself — until a valid key is entered.

  • The vendor generates a key signed with a private key that never ships to a customer.
  • You paste it in. The signature is checked against a public key baked into the app — no internet required.
  • On success the licence binds to this machine's hardware fingerprint, stored one-way hashed.
  • Copying an activated installation's data to a different machine fails closed.
Two disclosures. Activation reads the machine fingerprint from Linux or macOS only — a Windows machine cannot currently be activated at all. And a fully-offline design cannot detect the same key being activated on two independently-fresh machines; that remains a vendor business process, not a technical control.

What holds across all of them

MySQL 8 is required — several migrations use raw MySQL-only CHECK constraints and setup fails outright on a lighter database. Nothing phones home. The database is not reachable from outside the machine. Backups are plain MySQL dumps that move freely between installs.

Upgrades

A deliberate operator action, never automatic: load the newer image, point the version tag at it, restart. Data lives in a separate volume, so pointing the tag back at the previous version rolls the application back without touching your sales history.

08.1 Gap Before you buy

Five things to check against your own situation.

Blocker

Windows machines cannot be activated

The licence binds to a hardware fingerprint read only from Linux or macOS. On any other platform activation throws and the installation stays permanently locked. If your booth laptop runs Windows, this must be resolved before purchase.

Operational

Backup is a command, not a button

There is no backup or restore anywhere in the interface, and nothing is scheduled or automatic. Protecting an event's takings means someone comfortable with a terminal running it — and remembering to. Restore from a real external drive has not yet been exercised end to end.

Operational

MySQL 8 must exist on the machine

There is no lightweight embedded-database option. Either you install and maintain MySQL 8 yourself, or you take the Docker path, which bundles it.

Setup

Email needs configuration or it silently does nothing

Pre-order notifications and onboarding codes only work if the mail settings are filled in at install time. Miss that step and nothing is sent — the attempt is logged as skipped rather than failing loudly. Mail is also sent synchronously, so a slow mail server makes saving a status change feel like the app has hung.

Security

Change the seeded passwords

The development seeder creates five accounts sharing one publicly documented password. If it is run on a real installation and the passwords are not changed, the shop is left wide open. Independent penetration testing has not been performed; the security review to date is white-box code review only.

08.2 Gap Rough edges in shipped features

Things that work, but not as completely as they look.

Payments

Payment proofs are collected but never verified in-app

Non-cash payments are stored as "pending" and nothing in the product ever marks them verified or rejected. The proof image is safely stored, but no screen displays it back — retrieving one means calling the API directly. As a consequence, the shift's payment-method breakdown reports cash only.

Purchasing

Material stock has no screen

Receiving a purchase order does correctly increase material stock and write its history, but there is nowhere in the interface to view either. Non-cash supplier payments do not complete, and re-editing an existing draft order's lines is unreliable.

Costing

Recipe cost does not feed profit reports

This is deliberate — overwriting the cost price that settlements already depend on would be a correctness risk. But it means building an accurate bill of materials does not, by itself, improve any profit figure. You read it and decide.

Exports

Six screens have an export button; four exports have none

Products, stock, sellers, categories, suppliers and materials export from the interface. Vendor prices, recipes, roles and users are exportable only by calling the endpoint directly. The invoice import template also ships with a dummy example row that must be deleted before the file will import.

Billing

Saved bank details never reach the invoice

Settings → Payment stores a bank name, account number and account holder, but only the free-text instructions box is copied onto an invoice. Type the account details into that box if you want them printed.

Scale

Ceilings you will not hit at a booth, but should know

Product and supplier pickers on the purchase-order form list the first 100 records. Deleting a draft purchase order and creating another the same day can collide on the generated number. There is no supported multi-terminal setup and no TLS, so a second device on the network is convenience, not a hardened deployment.

08.3 Gap Roadmap

What the gaps point to next.

NEAR TERM

Close the honesty gaps

Windows fingerprint support. A backup button in the interface. Payment-proof viewing and verification. A material stock screen. The missing export buttons. These are small, well-understood pieces of work that remove the sharpest edges above.

MEDIUM TERM

Operational hardening

Scheduled backups, restore rehearsed against real removable media, dependency vulnerability scanning, security headers, and a continuous integration pipeline so a release never depends on someone remembering to run the tests.

LONGER TERM

The Android tablet build

Fully specified with two rejected alternatives documented, but the runtime binaries have not been sourced and the bundled database's licensing obligations are unresolved. Treat any delivery date as unestimated until both land.

What is deliberately not on this roadmap: a cloud tier, an online storefront, a subscription, or an artist self-service portal. Those would change what BoothPOS is — a local, one-time-licence till that holds your data on your own machine.
08.4 Gap Internal only — remove before sending to a customer

Delivery-side findings.

This slide is for the internal audience only. It records gaps in how the product is being delivered rather than in what it does, and it is not part of the customer-facing narrative.
Verification

Feature 019 (billing & invoicing) shipped without its manual verification steps completed

On a codebase whose own history shows real-browser checks catching defects the automated suite passed, this is the least-verified area in the product. The fact-check in preparing this deck independently found eight inaccuracies there.

Process

No CI pipeline

Every release depends on a developer remembering to run the suite locally. Feature 015 demonstrated the concrete risk when ten always-broken tests went unnoticed.

Docs

Project documentation carries stale claims

CLAUDE.md states the suite is 214 backend and 44 frontend tests; the measured figures are 492 and 223. The schema document covers roughly half the current schema. Statements made from these documents can be wrong in both directions.

Security

Unscanned and unreviewed areas

Dependency vulnerability scanning has never been run, so exposure is unknown rather than known-good. Formula injection is possible on every Excel export. Payment-proof images have no retention or deletion path.

Docker

Two concrete defects in the store deployment path

The release tarball's image tag does not match the compose file's default, so the documented offline start command falls back to building from source. And storage:link is never run on first boot, so uploaded images and QR codes return 404 in the Docker install.
